# iOS 定位耗电分析、理想形态与前台注意事项 v0.1

更新日期：2026-06-07

## 文档目标

本文说明 iPhone / iOS 定位耗电的根本原因、最终理想形态和前台使用注意事项。

当前 Apple Watch 徒步 MVP 的主线不变：

1. Apple Watch 是行进中导航、偏航判断、轨迹记录和本地兜底保存的主设备。
2. iPhone 负责路线准备、路线同步、低频状态展示和结束后复盘。
3. iPhone 首屏定位卡只作为当前位置展示、路线准备辅助和调试入口，默认不写入 Watch 徒步会话轨迹。
4. iPhone 后台持续定位、长时间稳定性、系统提示和耗电表现仍需真机验证，不能写成已实测结论。

## 耗电根本原因

iOS 定位耗电的根本问题不是“开启定位”本身，而是后台持续定位把整条业务链路一起带活。

单纯的系统定位已经有成本；如果每个定位点都触发地图、计算、日志、存储和 UI 分发，耗电会被放大。

应避免的后台链路：

```text
定位点到达
  -> 每点业务分发
  -> 地图蓝点 / 轨迹线刷新
  -> 路线匹配 / 偏航计算
  -> 里程 / 爬升 / 速度重算
  -> 诊断 JSON 写入
  -> 数据库 / KV 高频写入
  -> UI 状态更新
```

这种模式下，后台耗电不再只是 GPS / GNSS 成本，而是：

```text
后台耗电 = 定位
        + 计算
        + I/O
        + 地图渲染
        + 跨模块分发
        + 诊断日志
        + UI 状态链路
```

真正需要控制的是“定位点到达后唤醒了多少不该在后台跑的工作”。

### 关键耗电放大点

| 放大点 | 根本问题 |
| --- | --- |
| 后台高频定位 | 用户不看屏时仍持续触发整条链路 |
| 双定位源并行 | Watch 已记录时，iPhone 又跑一套高精度定位 |
| 每点地图刷新 | 后台或前台高频重绘轨迹、蓝点、辅助线 |
| 每点路线计算 | 路线投影、偏航判断、剩余距离计算随点高频运行 |
| 每点持久化重写 | 小状态、缓存或诊断日志被当成轨迹数据高频写 |
| 大体积诊断日志 | 正常使用时写入调试级 JSONL |
| UI 状态分发 | 定位点进入 Rx / Observable / EventBus 后带动大量无效更新 |

## 最终理想形态

### Apple Watch MVP

理想形态是端职责清晰，iPhone 不成为第二套行进主定位系统。

```text
Apple Watch：
  主定位
  主轨迹
  主偏航
  本地兜底保存
  结束后分块回传

iPhone：
  路线准备
  路线同步
  低频状态接收
  结束后复盘
```

Watch 徒步记录中，iPhone 不应自动开启高频后台定位，也不应因 Watch 断连就用 iPhone 后台定位补一条正式轨迹。

理想状态：

```text
Watch 记录中 + iPhone 前台 = 低频展示和辅助查看
Watch 记录中 + iPhone 后台 = 接收、保存、等待复盘，不跑地图和重计算
非记录 + iPhone 后台 = 基本静默
```

### 未来手机记录模式

如果后续支持“不带 Watch，仅用 iPhone 记录徒步”，理想架构应拆成两层。

后台只保留采集层：

```text
iOS 原生 CLLocationManager
  -> 原始定位点
  -> 内存小缓存
  -> SQLite 轻量落盘
```

正式存储优先使用 SQLite。它适合长时间追加、按 `sessionId` 和时间查询、去重排序、崩溃恢复和回前台批量补处理；JSONL 更适合调试导出，二进制 chunk 可留到后期极致体积或写入性能优化时再评估。

轻量落盘方案对比：

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| SQLite | 可靠、支持事务和索引，便于按会话和时间查询、去重、排序、恢复未完成会话 | 实现复杂度略高，需要设计表结构和批量写入策略 | 正式轨迹原始点存储优先使用 |
| JSONL | 追加写简单、可读性好、调试和导出方便 | 文件变大后查询、去重、截断、局部损坏恢复和版本演进都更麻烦 | 适合调试日志、问题复现和临时导出 |
| 二进制 chunk | 体积小、写入快、可按 chunk 控制文件大小 | 可读性差，版本兼容、排障、数据迁移和工具链成本高 | 后期极致性能或体积优化时再评估 |

性能直观对比：

以下为方案评估分，5 分最好，1 分最弱；不是实机 benchmark 数值。

| 维度 | SQLite | JSONL | 二进制 chunk |
| --- | --- | --- | --- |
| 追加写入性能 | 4 | 4 | 5 |
| 大数据查询性能 | 5 | 2 | 3 |
| 去重 / 补处理效率 | 5 | 2 | 3 |
| 崩溃恢复能力 | 5 | 2 | 3 |
| 文件体积控制 | 4 | 2 | 5 |
| CPU 开销 | 4 | 3 | 5 |
| 调试可读性 | 3 | 5 | 1 |
| 工程复杂度友好度 | 4 | 5 | 2 |
| 版本演进友好度 | 5 | 3 | 2 |
| 综合推荐度 | 5 | 3 | 2 |

直观结论：

| 方案 | 最强项 | 最大短板 |
| --- | --- | --- |
| SQLite | 查询、去重、恢复、长期维护最均衡 | 需要设计表结构和批量事务 |
| JSONL | 最容易写、最容易看 | 数据变大后查询和恢复弱 |
| 二进制 chunk | 写入和体积最强 | 调试、兼容、恢复和工具链成本高 |

结论：

```text
正式存储 = SQLite
调试导出 = JSONL
后期专项优化 = 二进制 chunk
```

内存小缓存只用于降低写入频率和合并批处理，不作为可靠数据源。推荐采用短队列或 ring buffer：

| 项 | 建议 |
| --- | --- |
| 缓存大小 | 100-300 个点 |
| 刷盘条数 | 每 5-20 个点批量写 SQLite |
| 刷盘时间 | 最多 10-30 秒写一次 |
| 强制刷盘 | 退后台、进入 inactive、停止记录、低电量、内存警告 |
| 快照 | 每次定位更新 `lastLocationSnapshot`，但低频持久化 |

核心原则：

```text
内存缓存 = 降低 I/O 和合并批处理
SQLite = 防丢数据的可靠来源
```

前台再恢复业务层：

```text
回前台
  -> 读取后台原始点
  -> 去重和排序
  -> 批量过滤
  -> 批量计算距离 / 爬升 / 路线状态
  -> 批量写业务数据
  -> 最后刷新一次地图
```

最终目标可以概括为：

```text
数据不丢
后台不跑重活
前台补算补渲染
```

理想后台耗电模型：

```text
后台耗电 = iOS 原生定位成本 + 极轻量落盘成本
```

而不是：

```text
后台耗电 = 定位 + 地图 + 导航 + 诊断 + 高频 I/O + UI 更新
```

## 前台注意事项

前台可以做更多工作，但仍要避免“每个点都全量刷新”。

### iPhone 前台定位

1. 首页和路线详情只在页面可见时按需定位。
2. 默认使用单次定位或低频定位即可。
3. 页面离开、App 退后台或不再需要蓝点时停止定位。
4. “持续高精度定位”只能作为用户主动开启的调试 / 辅助能力。
5. 高精度定位入口应明确提示耗电和后台权限含义。

### Watch 记录中打开 iPhone

1. iPhone 以 Watch `sessionStatus` 和回传 chunk 为准，不自己生成正式轨迹。
2. iPhone 地图只展示最近状态和辅助预览，不抢 Watch 主导航职责。
3. 轨迹线按 chunk 或低频节流刷新，不按每个点全量重绘。
4. 路线进度、偏航状态和剩余距离以 Watch 端结果为主。
5. iPhone 不把低频状态同步误当作完整历史事实。

### 前台地图刷新

1. 当前定位点可以较频繁更新，但轨迹线不必每点重绘。
2. 地图相机跟随、路线辅助线和复杂标记应限频。
3. 复盘页打开时再做完整轨迹绘制和统计。
4. 大路线或长轨迹需要分段渲染，避免一次性重绘造成卡顿和耗电。
5. 用户没有看地图时，不应继续维持地图活跃刷新。

### 前台计算和写入

1. 定位点进入业务层后先做可信度判断，低可信点不要触发偏航或重计算。
2. 距离、爬升、偏航、路线投影等计算可以增量处理，不要每次从头扫全量轨迹。
3. 轨迹数据可以按点或小批量保存，但非关键状态缓存应限频写入。
4. 诊断日志默认写 summary，完整逐点日志只在调试模式开启。
5. UI 状态更新应按展示需要节流，不要让每个定位点带动所有页面刷新。
