# iOS 定位耗电分析、最终目标与优化方案 v0.1

更新日期：2026-06-07

## 文档目标

本文根据 `/Users/ldy/Desktop/work/hike/docs/ios_location_power_strategy.md` 的省电思路，整理当前 Apple Watch 徒步 MVP 中 iPhone / iOS 定位链路的耗电边界、目标状态和后续优化方案。

当前产品主线仍是 Apple Watch 首发：

1. Apple Watch 是行进中导航、偏航判断、轨迹记录和本地兜底保存的主设备。
2. iPhone 负责路线准备、路线同步、低频状态展示和结束后复盘。
3. iPhone 首屏定位卡可作为当前位置展示、调试入口和路线准备辅助，但默认不写入 Watch 徒步会话轨迹。
4. iPhone 后台持续定位、长时间稳定性、系统提示和耗电表现仍需真机验证，不能写成已实测结论。

## 核心结论

省电目标不是简单关闭定位，而是拆清楚“谁在记录”“什么时候需要持续定位”“哪些工作可以延后”。

推荐原则：

```text
非徒步记录场景：iPhone 定位按需使用，退后台即停止持续定位。
Watch 徒步记录中：Watch 负责主轨迹；iPhone 不并行跑高频持续定位。
未来手机记录模式：后台只保留原生定位采点和轻量落盘，回前台再批量处理。
```

如果 iPhone 在后台持续做定位、地图刷新、路线匹配、诊断日志和 UI 状态分发，会把耗电从“系统定位成本”放大成整条业务链路成本。

理想模型：

```text
后台耗电 = iOS 原生定位成本 + 极轻量缓存 / 落盘成本
```

应避免的模型：

```text
后台耗电 = 定位
        + 每点业务分发
        + 地图刷新
        + 路线匹配
        + 偏航计算
        + 大体积诊断日志
        + 频繁数据库 / KV 写入
        + UI 状态更新
```

## 当前 MVP 中的 iPhone 定位职责

### iPhone 可承担的定位任务

| 场景 | 是否需要持续定位 | 建议策略 |
| --- | --- | --- |
| 首页或路线详情显示当前位置 | 否 | 页面可见时按需启动，页面离开后停止 |
| 路线准备时查看当前位置到起点距离 | 否 | 前台短时定位或单次定位 |
| Watch 出发检查 | 否 | 展示权限和最近可用位置，不启动后台记录 |
| 行进中状态页 | 否 | 以 Watch `sessionStatus` 为主，iPhone 不作为主导航 |
| 运动后复盘 | 否 | 使用 Watch 回传轨迹 |
| iPhone 调试定位卡 | 可选 | 仅作为调试和展示，不写入 Watch 会话 |
| 未来手机独立记录模式 | 是 | 需要单独设计后台原生采集和轻量持久化 |

### iPhone 不应承担的任务

在 Apple Watch MVP 中，iPhone 不应默默变成第二套行进中主定位系统：

1. 不远程开始、暂停、继续或结束 Watch 徒步。
2. 不在 Watch 记录时并行生成另一条正式轨迹。
3. 不用 iPhone 后台定位替代 Watch 偏航判断。
4. 不在后台持续刷新地图蓝点、路线辅助线或诊断 UI。
5. 不因 Watch 断连就自动开启 iPhone 高精度后台定位，除非用户进入明确的手机记录模式。

## App 状态耗电分析

### 非记录 + 前台

允许 iPhone 普通定位按需运行。

适用能力：

1. 首页地图蓝点。
2. 路线详情定位展示。
3. 当前位置到路线起点距离。
4. 调试定位卡。

建议：

1. 默认使用 `requestLocation()` 或低频 `startUpdatingLocation()`。
2. 页面不可见时停止页面定位同步。
3. 只有用户打开“持续高精度定位”调试入口时，才进入更高频定位。
4. 高精度定位入口应明确提示耗电和后台权限含义。

### 非记录 + 后台

必须停止所有持续定位。

目标状态：

```text
非记录 + 后台 = 基本静默
```

应停止：

1. iPhone 普通持续定位。
2. heading / 方向更新。
3. 地图当前位置同步。
4. 地图轨迹、标记或辅助线重绘。
5. 调试定位日志的逐点写入。

如果没有正在进行的手机记录模式，iPhone 退后台后继续高精度定位只会增加耗电和系统隐私提示风险。

### Watch 记录中 + iPhone 前台

iPhone 可以展示 Watch 低频状态，但不应抢主控。

允许：

1. 展示 Watch 是否 active / paused / finished。
2. 展示最近同步时间、Watch 电量、轨迹点数和偏航状态。
3. 接收 `sessionStatus`、`trackChunk`、`eventChunk`。
4. 必要时展示 iPhone 自身当前位置作为辅助调试信息。

避免：

1. iPhone 自身持续高频定位。
2. iPhone 实时重算 Watch 会话的偏航和路线进度。
3. iPhone 地图按每个 Watch 点实时重绘整条轨迹。
4. iPhone 把低频状态同步误当作完整历史事实。

### Watch 记录中 + iPhone 后台

iPhone 应以系统队列和本地持久化为主，不做实时重计算。

允许：

1. WatchConnectivity 后台可靠队列接收。
2. 接收后按幂等规则保存 `trackChunk` / `eventChunk` / `sessionSummary`。
3. 必要时更新轻量同步状态。

暂停：

1. iPhone 自身持续定位。
2. 地图渲染。
3. 复盘指标重算。
4. 大体积逐点诊断日志。
5. 高频 UI 状态更新。

目标状态：

```text
Watch 记录中 + iPhone 后台 = 接收与保存优先，不跑前台体验链路
```

### 未来手机记录模式 + 后台

如果后续增加“只带 iPhone 徒步记录”能力，应采用两层架构。

采集层：

1. iOS 原生 `CLLocationManager`。
2. `allowsBackgroundLocationUpdates = true` 仅在用户明确开始手机记录后启用。
3. 后台持续定位。
4. 原始点轻量缓存和持久化。

业务处理层：

1. 轨迹过滤。
2. 里程、爬升和速度计算。
3. 地图渲染。
4. 导航和偏航判断。
5. 诊断日志。

后台只保留采集层，业务处理层回前台后批量补算。

## 数据不丢策略

### Watch MVP

Watch 是主写入端：

1. 每个正式定位点先写入 Watch 本地。
2. Watch 断连时继续记录。
3. 结束后通过 WatchConnectivity 分块回传。
4. iPhone 按 `sessionId + sequence` 去重和检查连续性。
5. iPhone 不依赖自己的后台定位补齐 Watch 轨迹。

### 未来手机记录模式

仅靠内存缓存不够稳。iOS 原生侧应保存原始点。

建议链路：

```text
CLLocation 回调
  -> 转换为最小 RawLocationPoint
  -> 写入 SQLite / JSONL / 二进制 chunk
  -> 回前台后批量交给业务层处理
```

最小字段建议：

| 字段 | 说明 |
| --- | --- |
| `timeMillis` | 定位时间 |
| `latitude` | 纬度 |
| `longitude` | 经度 |
| `altitude` | 海拔 |
| `speed` | 速度 |
| `course` | 方向 |
| `horizontalAccuracy` | 水平精度 |
| `verticalAccuracy` | 垂直精度 |
| `source` | 定位来源 |
| `trustedLevel` | 后续过滤可信度 |

后台不建议保存地址、地图匹配详情、偏航状态解释或大体积调试上下文。

## 耗电来源拆解

| 来源 | 耗电风险 | MVP 策略 |
| --- | --- | --- |
| GPS / GNSS 定位 | 高 | 只在明确需要时持续运行；Watch 为主 |
| 高精度 + 高频采样 | 高 | 按电量和场景降频 |
| heading / 方向传感器 | 中 | 页面需要时启动，后台停止 |
| 地图渲染和轨迹重绘 | 中到高 | 后台停止，前台限频 |
| 路线匹配 / 偏航计算 | 中 | Watch 端行进中执行；iPhone 后台暂停 |
| WatchConnectivity 实时状态 | 中 | 低频、状态变化优先，结束后补传完整数据 |
| 逐点数据库 / KV 写入 | 中 | 轨迹 chunk 化；非轨迹状态限频写 |
| 大体积诊断 JSON | 中 | 默认 summary，调试模式才完整 |
| UI 状态分发 | 低到中 | 前台可用，后台停止 |

## 最终目标

### 产品目标

1. 用户在 Watch 上徒步时，轨迹不丢、偏航能提醒、结束能同步。
2. iPhone 不因为辅助展示而显著增加整套系统耗电。
3. 没有明确手机记录模式时，iPhone 后台基本静默。
4. iPhone 定位权限和后台定位用途清晰，避免用户误以为 App 一直在手机后台追踪。
5. 后续如支持手机独立记录，也能做到后台轻采集、前台补处理。

### 技术目标

```text
Apple Watch MVP：
  Watch = 主定位 + 主轨迹 + 主偏航 + 本地兜底
  iPhone = 路线准备 + 状态接收 + 复盘展示

未来手机记录模式：
  后台 = 原生采点 + 轻量落盘
  前台 = 批量补算 + 一次刷新
```

### 验证目标

需要用 iPhone + Apple Watch 真机验证：

1. iPhone 非记录退后台后是否停止持续定位。
2. Watch 记录中 iPhone 不开后台定位时，路线同步和会话回传是否仍可靠。
3. iPhone 前台状态页长时间打开时的地图刷新耗电。
4. “持续高精度定位”调试入口退后台后的系统提示、耗电和调度表现。
5. Watch 端 1 小时、4 小时、8 小时记录下的电量曲线和轨迹完整性。

## 进一步优化方案

### P0：明确 iPhone 定位开关语义

将 iPhone 首屏定位卡定义为“前台辅助定位 / 调试定位”，而不是正式会话记录。

要求：

1. 默认只在页面可见时定位。
2. 离开页面或 App 退后台时停止普通定位。
3. “持续高精度定位”必须是用户主动开启。
4. UI 文案说明它不替代 Watch 徒步记录。

### P0：Watch 记录时禁止 iPhone 双源高频记录

Watch 会话 active 时，iPhone 不自动启动高频后台定位。

例外：

1. 用户主动进入未来的手机记录模式。
2. 开发调试开关明确开启。
3. 真机验证任务临时需要采样对比。

这些例外都不应写入正式 `HikingSession` 轨迹，除非产品另行定义数据归属。

### P1：iPhone 地图刷新限频

行进中状态页可展示 Watch 最近位置，但应限制刷新：

1. 前台每 5-15 秒刷新一次状态即可。
2. 轨迹线可按 chunk 或状态变化刷新。
3. 后台不刷新地图。
4. 复盘页打开时再做完整绘制和统计。

### P1：同步接收与复盘计算解耦

iPhone 接收 Watch 数据时先保存，再按页面需要计算。

建议：

1. `trackChunk` 到达后先幂等落盘。
2. 前台复盘页再计算距离、偏航段展示和统计。
3. 后台只维护轻量完整性状态。
4. 缺失范围由 ACK 机制处理，不靠实时 UI 驱动。

### P1：诊断日志分级

默认不要逐点写完整诊断。

建议模式：

| 模式 | 写入内容 |
| --- | --- |
| 正常 | session summary、错误摘要、关键事件 |
| 调试 | 可开启逐点 JSONL |
| 后台 | 点数、时间范围、最大误差、错误计数 |
| 结束 | 完整摘要和必要上下文 |

后台 summary 可包含：

```text
rawPointCount
acceptedPointCount
firstTimeMillis
lastTimeMillis
maxHorizontalAccuracy
minHorizontalAccuracy
errorCount
```

### P2：未来手机记录模式的原生持久化

若要支持 iPhone 独立徒步记录，优先补齐原生侧轻量持久化：

1. 原始定位点按 chunk 写 SQLite / JSONL。
2. 写入失败要有错误计数和最后错误摘要。
3. App 被系统杀掉后，重新打开能发现未完成手机会话。
4. 回前台后批量补点，批量写业务表，最后一次刷新地图。

### P2：基于状态的采样策略

未来可以按用户状态动态调整：

| 状态 | 建议 |
| --- | --- |
| 正常移动 | 标准采样 |
| 停留或速度很低 | 降低采样和地图刷新 |
| 接近路线关键点 | 临时提高采样 |
| 偏航中 | 保持较高可信采样 |
| 低电量 | 降低采样、暂停实时同步 |
| 暂停中 | 低频保留当前位置，不写正式轨迹 |

该策略需要真机和实地验证，不能只按模拟器表现定稿。
